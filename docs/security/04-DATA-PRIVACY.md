# 04. Data Privacy & Row-Level Authorization

This document explains the row-level security mechanisms implemented in the backend.

## Overview
While `@RequirePermissions` enforces endpoint-level access, data privacy mandates that users only access rows belonging to their department, scope, or direct ownership.

## The `rbac.util.ts` Framework
The backend leverages `getAdvancedScope()` and its wrapper `getSalesScope()` to inject Prisma `Where` conditions dynamically based on the requesting user's identity.

```typescript
// Example from customers.service.ts
const scope = getSalesScope(userId, role, 'createdById');
const customer = await this.prisma.customer.findFirst({
  where: { id, companyId, ...scope, deletedAt: null },
});
```

### 1. Sales Domain Ownership
Users with role `SALES_EXECUTIVE` or `SALES_INTERN` are strictly restricted to entities where `createdById` matches their `userId`. This ensures a sales executive cannot query or manipulate customers or sales orders generated by their peers.

### 2. Department-Level Filtering
Users belonging to domains like `PRODUCTION` or `FINANCE` have distinct visibility scopes tailored for cross-department interactions (e.g., Finance viewing finalized sales orders without being able to edit the underlying CRM notes). 
If a user is a `SUPER_ADMIN` or falls into the `OTHER` administrative bracket, `getAdvancedScope()` returns an empty scope object `{}`, implicitly allowing unrestricted global read/write across the company.

### 3. Multi-Tenancy (Company Isolation)
Regardless of the RBAC or Row-Level security scope, all queries rigorously mandate `where: { companyId: req.user.companyId }`. This acts as an inescapable multi-tenant boundary.
