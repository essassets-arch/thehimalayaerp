# 05. Remaining Risks

This document outlines structural risks and edge-cases remaining in the backend after the primary hardening pass.

## 1. Missing Record-Level Checks in Specific Domains
While `getSalesScope()` correctly restricts domains like CRM and Sales, some adjacent domains (e.g., Procurement Indents, HR Documents) may lack explicit row-level filters. This means an executive in Procurement might be able to query Indents generated by another executive if they bypass the UI and hit the API directly.
**Recommendation:** Implement `getProcurementScope()` and `getHrScope()` analogues and wire them into the respective Prisma `.findMany()` queries.

## 2. Hardcoded Admin Bypass
The `getAdvancedScope()` utility forces `OTHER` domains (like `SUPER_ADMIN`) into a `{}` unbounded query scope. If an administrative role is compromised, the attacker has unrestricted database access across the entire company.
**Recommendation:** Enforce logical partitions even for admins, requiring explicit escalation (e.g., sudo mode) to fetch globally cross-department data.

## 3. Optimistic Concurrency Misses
Several endpoints enforce `expectedVersion` to prevent race conditions during updates (e.g., `customers.controller.ts`), but not all endpoints across the system strictly require version checks during `PATCH` operations.
**Recommendation:** Enforce `version` checking globally on all `update` and `delete` mutations to ensure atomicity.

## 4. Rate Limiting
Public endpoints like `/auth/login` and `/hr/salary-slips/shared/:token` currently lack explicit rate limiting in the controller logic. They are vulnerable to brute-force credential stuffing and token-guessing attacks.
**Recommendation:** Integrate `@nestjs/throttler` to tightly bound requests to these `@Public()` pathways.
