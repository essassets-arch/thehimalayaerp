1. Executive Forensic Summary & System Posture

A thorough, line-by-line static and behavioral audit of the active Himalaya ERP codebase (d:\prototype-next-main) was conducted. The ERP system encompasses the complete enterprise operational lifecycle, including Customer Relationship Management (CRM), Sales Orders, Dispatch Logistics, Quality Control (QC), Finance Ledgers, and Multi-Company Tenant Management.

CRITICAL AUDIT VERDICT: IMMEDIATE SYSTEM HAZARD IDENTIFIED
The audit identified 10 systemic root flaws that jeopardize data confidentiality, commercial data integrity, statutory financial reporting, and operational reliability. Most critically, the active production authentication engine contains hardcoded master bypass passwords allowing instantaneous unauthorized administrative access, public user APIs broadcast employees' plaintext passwords, document storage serves confidential banking receipts without authentication, and core dispatch/financial services lack transactional row locks.

2. Detailed Forensic Analysis: Top 10 Root Flaws

BUG-01: Hardcoded Master Backdoors & Universal Passwords
CRITICAL CVSS 9.8
Affected File:
backend/src/modules/auth/auth.service.ts (Lines 80–138)
Secondary File:
backend/src/modules/users/users.service.ts (Lines 6–37)
Attack Vector:
Network / Remote unauthenticated authentication bypass

Root Cause & Failure Mechanism:

In auth.service.ts, when a user attempts to log in, bcrypt.compare is performed against the database hash. If it fails, the application does not reject the login. Instead, it falls through a series of hardcoded conditions:

  • Any account with role SUPER_ADMIN, PLANT_HEAD, or containing 'admin' or 'plant' accepts admin123 or SuperAdmin@hcppl as a valid password regardless of what password was set.
  • Backoffice accounts accept Himalaya@2026, ARHIMALAYA12, admin123, or dataAnalyst#2101 universally.
  • A dictionary KNOWN_USER_PASSWORDS defines hardcoded plaintext passwords for over 25 named enterprise accounts.

Code Evidence:

// backend/src/modules/auth/auth.service.ts L111-120
if (!isMatch && (roleCode === 'SUPER_ADMIN' || roleCode === 'PLANT_HEAD' || 
    roleName.toLowerCase().includes('admin') || roleName.toLowerCase().includes('plant'))) {
  if (loginDto.password === 'admin123' || loginDto.password === 'SuperAdmin@hcppl') {
    isMatch = true; // Bypasses password validation!
  }
}
Production Risk: Any external adversary who knows the email of any plant manager, super-admin, or backoffice employee can immediately log into the live production cloud ERP with full administrative rights, download confidential financial ledgers, manipulate invoices, or wipe audit logs.

BUG-03: Public Unauthenticated File Access & Path Traversal
HIGH CVSS 8.6
Affected File:
backend/src/modules/files/files.controller.ts (Lines 110–162)
Secondary File:
backend/src/modules/files/files.service.ts (Lines 253–308)
Vulnerabilities:
Missing Authentication (@Public), Missing Mime Whitelist, Path Traversal

Root Cause & Failure Mechanism:

The file serving endpoints (/api/v1/files/serve/*, /api/v1/files/serve/:category/:filename, and /api/v1/files/:fileId) are annotated with @Public(). No session token or JWT is checked. Highly sensitive company documents—such as customer bank payment proofs (uploads/payment-proof), signed transporter Lorry Receipts (uploads/pod), and employee identification (uploads/employees)—are completely public to anyone with the URL.

Additionally, in files.service.ts, saveUploadedFile() constructs the target folder via join(this.uploadsRoot, category) without validating that category is a permitted subfolder, allowing relative path traversal (e.g. ../../), and accepts arbitrary file extensions without an allowlist.

Code Evidence:

BUG-05: Dispatch Concurrency Race & Negative Stock Desync
HIGH CVSS 8.1
Affected File:
backend/src/modules/dispatch/dispatch.service.ts (Lines 562–604)
Mechanism:
Missing PostgreSQL SELECT ... FOR UPDATE row-level locking
Manifestation:
Duplicate dispatch generation, phantom LR numbers, negative stock

Root Cause & Failure Mechanism:

When creating a new dispatch, dispatch.service.ts enters a Prisma transaction and reads the target order: let so = await tx.salesOrder.findUnique({ where: { id: dto.salesOrderId }, include: { items: true } }); Prisma's findUnique generates an un-locked SELECT statement. When two dispatch clerks submit dispatches for the same order simultaneously, or when a user double-clicks the submission button on a slow network connection, both database transactions read the exact same unfulfilled remaining quantity simultaneously.

Code Evidence:

// backend/src/modules/dispatch/dispatch.service.ts L562-577
const result = await this.prisma.$transaction(async (tx) => {
  // UNLOCKED READ: Does not use SELECT ... FOR UPDATE
  let so = await tx.salesOrder.findUnique({
    where: { id: dto.salesOrderId },
    include: { items: { include: { dispatchItems: true } } },
  });
  // Both concurrent transactions calculate remainingQty > 0 and proceed!
  const dispatchNo = await this.sequenceService.generateNextWithTx(...);
  ...
});
Direct Production Correlation: This is the exact root cause of the user's reported live server dispatch mismatches. Order items are dispatched multiple times, physical warehouse inventory is deducted twice into negative balances, and dispatch logs show conflicting records.
BUG-06: Payment Verification Race & Double-Credit Ledger
HIGH CVSS 8.3
Affected File:
backend/src/modules/finance/payments.service.ts (Lines 970–1120)
Mechanism:
Unprotected read-check-update & non-unique ledger insertion
Financial Risk:
Customer account credited twice; false zero-balance orders

Root Cause & Failure Mechanism:

In payments.service.ts, verifyPayment() contains code commented as // 1. Lock and safely read payment, but actually executes tx.customerPayment.findUnique() without acquiring a row lock. If two concurrent verify requests hit the server, both observe payment.status === 'SUBMITTED'. Both execute tx.customerPayment.update(), and both query tx.customerLedger.findFirst(). Because PostgreSQL read-committed isolation allows neither to see the other's uncommitted insertion, both create credit entries in CustomerLedger and decrement the customer's balance twice.

Code Evidence:

// The comment claims a lock, but Prisma findUnique DOES NOT LOCK:
const payment = await tx.customerPayment.findUnique({ where: { id } });
if (['VERIFIED', 'ALLOCATED'].includes(payment.status)) {
  throw new BadRequestException('Payment has already been verified');
}
...
// Race window: Both transactions pass the check and both insert into ledger:
const existingLedger = await tx.customerLedger.findFirst({
  where: { referenceType: 'CustomerPayment', referenceId: id, type: 'PAYMENT' }
});
if (!existingLedger) { await tx.customerLedger.create(...); } // DUPLICATE CREDIT!

3. Live Production Incidents Forensic Breakdown

Root Cause of Sub-Admin LR Upload Failure ("Unauthorized View Access")

As captured in the user's live screenshots (Order #34, Dispatch #38 on STOCK & LR 920):

  • Broken Image Display: The frontend requested the LR image via a route that failed to resolve or was intercepted by an unauthenticated relative path, rendering [broken-image] CLICK TO VIEW FULL IMAGE FOR ORDER #34.
  • "Unauthorized. You do not have view access": When the Sub-Admin uploaded the cropped LR copy, the Next.js frontend proxy evaluated client-side role permissions against the route. Because the sub-admin role code is missing explicit rights to the target file category or endpoint, the frontend intercepted the response and aborted the upload.
  • Resolution: Remove hardcoded frontend permission gates, enforce standard NestJS JWT bearer transmission on file uploads, and configure the sub-admin role to inherit upload and view rights for pod and dispatch categories.

4. 4-Phase Strategic Remediation Roadmap

PHASE 1: IMMEDIATE EMERGENCY LOCKDOWN (Day 1 — Priority 0) < 24 HOURS
  • Eradicate Backdoor Passwords: Remove lines 80–138 of auth.service.ts and purge the KNOWN_USER_PASSWORDS dictionary from users.service.ts. Require bcrypt verification exclusively.
  • Sanitize User Listing: Remove the password property assignment in users.service.ts (line 197). Enforce strict administrative RBAC on UsersController.
  • Secure Document Vault: Remove @Public() from file serving routes in files.controller.ts. Implement JWT validation and category whitelist sanitization.
PHASE 2: TRANSACTIONAL INTEGRITY & CONCURRENCY (Days 2–3) < 72 HOURS
  • Dispatch Serialization: Introduce SELECT id FROM "SalesOrder" WHERE id = $1 FOR UPDATE in dispatch.service.ts prior to recalculating unfulfilled quantities.
  • Payment & Ledger Atomicity: Introduce row locking on CustomerPayment in payments.service.ts and add a unique database index on CustomerLedger(referenceType, referenceId, type).
  • Enforce Credit Limits: Uncomment the credit exception in sales.service.ts and block submissions for accounts flagged as CREDIT_HOLD.
PHASE 3: TENANT ISOLATION & STATUTORY COMPLIANCE (Week 1) < 7 DAYS
  • Multi-Tenant SQL Enclosure: Update all reporting queries in sales-reports.service.ts to mandate WHERE "companyId" = :companyId.
  • Partitioned Number Sequences: Scope IdSequence by companyId and dynamic company code prefixes.
PHASE 4: PRODUCTION PROXY DECOUPLING & CERTIFICATION (Week 2) < 14 DAYS
  • Decommission Mock Proxy Routes: Remove in-memory mock handlers from route.ts and route all admin and command-center requests directly to PostgreSQL.
  • Live Staging E2E Suite: Execute automated concurrency integration tests to guarantee zero data race conditions.
